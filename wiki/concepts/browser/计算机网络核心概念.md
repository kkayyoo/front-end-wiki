# 计算机网络核心概念

## HTTP vs HTTPS

| 对比 | HTTP | HTTPS |
|---|---|---|
| 传输 | 明文 | SSL/TLS 加密 |
| 端口 | 80 | 443 |
| 证书 | 不需要 | 需要 CA 证书 |
| 性能 | 快 | 握手阶段额外耗时 |

### HTTPS 工作原理

1. 客户端发起 HTTPS 请求
2. 服务器返回**数字证书**（含公钥）
3. 客户端验证证书合法性，协商加密等级
4. 客户端生成**会话密钥**（对称密钥），用服务器公钥加密后发送
5. 服务器用私钥解密，获得会话密钥
6. 双方用**会话密钥进行对称加密通信**（后续通信都用对称加密，速度快）

> **关键点**：HTTPS 是非对称加密（RSA）+ 对称加密（AES）混合使用。非对称加密用于安全传输会话密钥，对称加密用于实际数据传输（因为非对称加密速度慢）。

## TCP 三次握手

```
客户端                服务端
  |----SYN(seq=j)---→|   第一次：客户端发 SYN，进入 SYN_SENT
  |←-SYN+ACK(ack=j+1)-|  第二次：服务端收到，发 SYN+ACK，进入 SYN_RECV
  |----ACK(ack=k+1)--→|  第三次：客户端发 ACK，双方进入 ESTABLISHED
```

**为什么需要三次？**
两次握手只能确认"客户端能发、服务端能收"，无法确认"服务端能发、客户端能收"。第三次握手确认双向通信都正常。

## TCP 四次挥手

```
客户端                服务端
  |-----FIN-------→|   第一次：客户端发 FIN，停止发送数据（主动关闭）
  |←----ACK--------|   第二次：服务端确认，进入 CLOSE_WAIT（可能还有数据要发）
  |←----FIN--------|   第三次：服务端发完数据，发 FIN
  |-----ACK-------→|   第四次：客户端确认，等待 2MSL 后进入 CLOSED
```

**为什么四次挥手？**
TCP 是全双工，两个方向独立关闭。服务端收到 FIN 后，可能还有数据没发完，所以 ACK 和 FIN 分两次发送（不像握手时合并成一次 SYN+ACK）。

**为什么 TIME_WAIT 等 2MSL？**
确保最后一个 ACK 能到达服务端（若丢失，服务端会重发 FIN，客户端需要在此期间重新 ACK）。

## TCP vs UDP

| 对比 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认+重传） | 不可靠 |
| 传输方式 | 单播 | 单播、多播、广播 |
| 速度 | 较慢（有流控/拥控） | 快 |
| 头部开销 | 大（20字节） | 小（8字节） |
| 场景 | HTTP、文件传输、邮件 | DNS、视频直播、游戏 |

> DNS 使用 UDP（速度快，查询小），TCP 三次握手太慢。

## HTTP 状态码

| 类别 | 含义 | 常见 |
|---|---|---|
| 1xx | 临时响应 | 100 继续 |
| 2xx | 成功 | **200** OK、201 已创建、204 无内容 |
| 3xx | 重定向 | **301** 永久、**302** 临时、**304** 未修改 |
| 4xx | 客户端错误 | **400** 语法错误、**401** 未授权、**403** 禁止、**404** 未找到 |
| 5xx | 服务端错误 | **500** 内部错误、**502** 错误网关、**503** 不可用、**504** 网关超时 |

## 浏览器缓存机制

### 强制缓存（不请求服务器）

控制字段：`Cache-Control`（优先级高）和 `Expires`（过期时间，受本地时间影响）

```
Cache-Control: max-age=31536000  // 缓存1年
Cache-Control: no-cache          // 每次都要协商缓存
Cache-Control: no-store          // 不缓存
```

### 协商缓存（请求服务器验证）

| 请求头 | 响应头 | 说明 |
|---|---|---|
| `If-None-Match` | `ETag` | 资源唯一标识（优先级高） |
| `If-Modified-Since` | `Last-Modified` | 最后修改时间 |

返回 **304**：缓存有效，用本地缓存  
返回 **200**：缓存失效，返回新资源

### 缓存决策流程

```
请求资源
  ↓
查强制缓存（Cache-Control/Expires）
  ↓
  命中且未过期 → 直接用缓存（200 from cache）
  未命中/过期 ↓
协商缓存（ETag/Last-Modified）
  ↓
  服务器验证：未修改 → 304 + 使用缓存
  服务器验证：已修改 → 200 + 新资源
```

## HTTP 跨域

### 同源策略

协议 + 域名 + 端口三者必须完全相同，否则跨域。

### 解决方案

**① CORS（主流方案）**

服务端设置响应头允许跨域：
```
Access-Control-Allow-Origin: https://yoursite.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
```

复杂请求（非简单请求）会先发 `OPTIONS` 预检请求。

**② Proxy 代理（开发环境）**

```typescript
// Angular 项目 proxy.conf.json
{
  "/api": {
    "target": "https://api.azure.com",
    "changeOrigin": true,
    "secure": false
  }
}
```

```json
// angular.json
"serve": {
  "options": { "proxyConfig": "proxy.conf.json" }
}
```

**③ JSONP**：只支持 GET，已过时，不推荐  
**④ Nginx 反向代理**：生产环境常用

> **实际项目**：Angular 开发环境用 proxy.conf.json，生产环境用 Nginx 配置 CORS 或反向代理。Azure 的 API 通常需要配合 CORS + 鉴权 token。

## HTTP/1.1 vs HTTP/2 vs HTTP/3

### HTTP/1.1 的问题

- **队头阻塞**：同一 TCP 连接请求需排队，前一个慢后面全堵
- **头部冗余**：每次请求都携带大量重复 Header
- **明文传输**：不安全
- **浏览器限制**：每个域名最多 6 个 TCP 连接

### HTTP/2 的改进

- **二进制分帧**：请求/响应拆分成二进制帧，效率更高
- **多路复用**：一个 TCP 连接，多个请求并行（解决了 HTTP 层队头阻塞）
- **Header 压缩（HPACK）**：减少重复头部传输
- **Server Push**：服务端主动推送资源

> ⚠️ HTTP/2 解决了 **HTTP 层**队头阻塞，但 **TCP 层**队头阻塞仍存在（TCP 丢包会阻塞所有流）

### HTTP/3 的改进（QUIC over UDP）

- 基于 **UDP**，引入 QUIC 协议
- **0-RTT/1-RTT** 建连（比 TCP 三次握手快）
- 彻底解决队头阻塞（每个流独立传输）
- 连接迁移：网络切换（WiFi→4G）不断连

## XSS / CSRF / DDoS 安全攻击

### XSS（跨站脚本攻击）

攻击者在网页注入恶意脚本，窃取 Cookie、Session 等。

**防御**：
- 对用户输入进行 HTML 转义（`<` → `&lt;`）
- 设置 `Content-Security-Policy` 头
- Cookie 设置 `HttpOnly`（JS 无法访问）

### CSRF（跨站请求伪造）

攻击者诱导用户访问恶意页面，该页面以用户身份向目标网站发请求。

**防御**：
- 使用 **CSRF Token**（每次请求携带服务端生成的随机 token）
- 验证 `Origin` / `Referer` 请求头
- SameSite Cookie 属性设置为 `Strict` 或 `Lax`

### DDoS（分布式拒绝服务）

大量请求耗尽服务器资源，使服务不可用。

**防御**：限流、WAF 防火墙、CDN 分散流量

## Cookie vs sessionStorage vs localStorage

| 对比 | Cookie | sessionStorage | localStorage |
|---|---|---|---|
| 大小限制 | ~4KB | ~5MB | ~5MB |
| 生命周期 | 设置过期时间 | 标签页关闭即清除 | 永久（手动删除）|
| 发送给服务器 | **自动携带** | 否 | 否 |
| 跨标签页 | 是（同源） | **否** | 是（同源）|
| 主要用途 | 认证（Session ID） | 临时页面状态 | 用户偏好/缓存 |

## WebSocket

全双工通信协议，建立在 TCP 上，握手阶段使用 HTTP，握手后脱离 HTTP 协议。

```typescript
// Angular 中使用 WebSocket（数据实时推送场景）
import { webSocket } from 'rxjs/webSocket';

const ws = webSocket('wss://api.azure.com/copy-jobs/status');

ws.subscribe(
  status => this.updateJobStatus(status),
  err => this.handleError(err)
);

// 发送消息
ws.next({ jobId: '123', action: 'subscribe' });
```

**vs 轮询**：WebSocket 是真正的实时双向通信，轮询是定时模拟，浪费资源。
