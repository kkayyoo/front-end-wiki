# 前端系统设计面试

## 1. 如何回答 60 分钟系统设计题

### RADIO 框架

前端系统设计面试的黄金框架（GreatFrontEnd 推荐）：

| 阶段 | 英文 | 时间 | 内容 |
|------|------|------|------|
| **需求澄清** | Requirements | 5-10 min | 功能需求、非功能需求、规模、设备、离线支持、实时性 |
| **架构设计** | Architecture | 15-20 min | 整体架构图、技术选型、数据流 |
| **数据模型** | Data Model | 10 min | 前端数据结构、接口设计、状态结构 |
| **接口定义** | Interface | 10 min | 组件 API、HTTP API、事件接口 |
| **优化方向** | Optimizations | 10-15 min | 性能、可访问性、错误处理、扩展性 |

### 开场澄清问题模板

```markdown
1. 规模：DAU 是多少？并发用户量？
2. 设备：需要支持移动端吗？桌面端优先还是移动优先？
3. 实时性：数据是否需要实时更新？WebSocket 还是轮询？
4. 离线支持：是否需要 PWA/Service Worker？
5. 国际化：多语言支持？RTL 语言？
6. 可访问性：WCAG 2.1 AA 标准？
```

### 6 年经验的回答角度

> "我会先问清楚业务场景——比如在 Azure Data Copy 里，数据表格可能有百万条记录，这直接决定了我是否需要虚拟滚动、分页还是流式加载。技术决策必须基于具体约束，而不是炫技。"

## 2. CSR vs SSR vs SSG vs ISR 渲染模式选型

### 对比表

| 模式 | 全称 | 渲染时机 | 适用场景 | 代表框架 |
|------|------|----------|----------|----------|
| **CSR** | Client-Side Rendering | 浏览器运行时 | 富交互应用（后台、数据可视化） | React SPA, Angular |
| **SSR** | Server-Side Rendering | 每次请求时服务端渲染 | SEO 敏感、个性化内容 | Next.js, Nuxt.js |
| **SSG** | Static Site Generation | 构建时渲染 | 博客、文档、内容不变的页面 | Next.js, Gatsby |
| **ISR** | Incremental Static Regeneration | 构建 + 定时/按需重生成 | 内容定期更新的页面 | Next.js |

### 决策树

```
需要 SEO？
├─ 是 → 内容变化频率？
│        ├─ 几乎不变 → SSG
│        ├─ 定期更新（分钟/小时级）→ ISR
│        └─ 实时/个性化 → SSR
└─ 否 → 富交互 Dashboard/后台 → CSR
```

### 代码示例：Next.js ISR（电商/内容平台）

```typescript
// pages/products/[id].tsx
import type { GetStaticProps, GetStaticPaths } from 'next';

interface ProductPageProps {
  product: Product;
}

export const getStaticProps: GetStaticProps<ProductPageProps> = async ({ params }) => {
  const product = await fetchProduct(params!.id as string);
  
  return {
    props: { product },
    revalidate: 60, // 每 60 秒重新生成（ISR）
  };
};

export const getStaticPaths: GetStaticPaths = async () => {
  const popularProducts = await fetchPopularProducts(100);
  
  return {
    paths: popularProducts.map(p => ({ params: { id: p.id } })),
    fallback: 'blocking', // 未预生成的页面按需生成（SSR 降级）
  };
};
```

### 面试问答

**Q: Azure Data Copy 这类 B2B 后台工具适合哪种渲染模式？**

> "CSR。原因：1) SEO 不重要（用户需要登录）；2) 高度交互性（实时状态更新、筛选、排序）；3) Angular 就是为 SPA 设计的，组件化很好用。如果有公开落地页需要 SEO，可以用 Next.js 做一个独立的 SSG/ISR 站点。"

## 3. 微前端架构（Module Federation）

### 适用场景

- 大型团队（5+ 个独立前端团队）
- 多个独立部署的子应用
- 需要渐进式迁移旧系统（Angular → React）

### Module Federation 核心概念

```
Host App (Shell)
├── Remote App 1 (Teams → Angular 17)
├── Remote App 2 (Billing → React 18)
└── Remote App 3 (Analytics → Vue 3)
```

### Webpack Module Federation 配置

```typescript
// webpack.config.ts - Host (Shell)
import { ModuleFederationPlugin } from 'webpack/container';

const hostConfig = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'shell',
      remotes: {
        // 运行时动态加载远程应用
        teams: 'teams@https://teams.example.com/remoteEntry.js',
        billing: 'billing@https://billing.example.com/remoteEntry.js',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.0.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.0.0' },
      },
    }),
  ],
};

// webpack.config.ts - Remote (Teams App)
const teamsConfig = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'teams',
      filename: 'remoteEntry.js',
      exposes: {
        './TeamsList': './src/components/TeamsList',
        './TeamDetail': './src/components/TeamDetail',
      },
      shared: {
        react: { singleton: true },
      },
    }),
  ],
};
```

### 在 Host 中使用远程组件

```typescript
// Shell App - 动态加载远程组件
import React, { lazy, Suspense } from 'react';

// 类型声明（Module Federation 远程模块）
declare module 'teams/TeamsList' {
  const TeamsList: React.ComponentType<{ orgId: string }>;
  export default TeamsList;
}

const TeamsList = lazy(() => import('teams/TeamsList'));

const App: React.FC = () => (
  <Suspense fallback={<LoadingSpinner />}>
    <TeamsList orgId="azure-data-copy" />
  </Suspense>
);
```

### 微前端 Trade-offs

| 优点 | 缺点 |
|------|------|
| 独立部署、独立技术栈 | 复杂度高（调试困难） |
| 团队自治 | 共享状态管理复杂 |
| 渐进式迁移旧系统 | 包体积可能增大 |
| 故障隔离 | 需要统一设计系统 |

## 4. 大型应用状态管理架构设计

### 状态分层原则

```
┌─────────────────────────────────────────┐
│  Server State（服务端状态）              │
│  React Query / SWR / Apollo             │
│  → API 数据、缓存、同步                  │
├─────────────────────────────────────────┤
│  Global UI State（全局 UI 状态）          │
│  Zustand / Redux Toolkit                │
│  → 主题、语言、用户信息、权限             │
├─────────────────────────────────────────┤
│  Feature State（功能模块状态）            │
│  Context API / Zustand slice            │
│  → 单个功能的本地全局状态                 │
├─────────────────────────────────────────┤
│  Component State（组件本地状态）          │
│  useState / useReducer                  │
│  → UI 交互状态、表单、临时数据            │
└─────────────────────────────────────────┘
```

### 选型建议

```typescript
// Server State: React Query（推荐）
const { data, isLoading, error } = useQuery({
  queryKey: ['copy-jobs', filters],
  queryFn: () => fetchCopyJobs(filters),
  staleTime: 30_000,        // 30s 内不重新请求
  gcTime: 5 * 60_000,       // 5 分钟后 GC
  refetchOnWindowFocus: true, // 切回页面自动刷新
});

// Global State: Zustand（轻量，无 boilerplate）
import { create } from 'zustand';

interface AppStore {
  theme: 'light' | 'dark';
  locale: string;
  user: User | null;
  setUser: (user: User | null) => void;
  toggleTheme: () => void;
}

const useAppStore = create<AppStore>((set) => ({
  theme: 'light',
  locale: 'en-US',
  user: null,
  setUser: (user) => set({ user }),
  toggleTheme: () => set((s) => ({ theme: s.theme === 'light' ? 'dark' : 'light' })),
}));
```

### Context 性能陷阱与解决

```typescript
// ❌ 问题：一个 Context 包含所有状态，任何更新触发所有消费者重渲染
const AppContext = createContext({ user, theme, notifications });

// ✅ 方案：拆分 Context，按关注点分离
const UserContext = createContext<User | null>(null);
const ThemeContext = createContext<'light' | 'dark'>('light');
const NotificationContext = createContext<Notification[]>([]);
```

## 5. 前端监控与错误追踪

### 监控体系

```
┌─────────────┬──────────────────────────────────────────┐
│ 监控类型     │ 工具/实现                                 │
├─────────────┼──────────────────────────────────────────┤
│ JS 错误      │ Sentry、自定义 window.onerror             │
│ 性能指标     │ Web Vitals API + 上报、Datadog RUM        │
│ 用户行为     │ Mixpanel、Amplitude                      │
│ API 监控     │ Axios interceptor + 上报、OpenTelemetry  │
│ 资源加载     │ PerformanceObserver                      │
└─────────────┴──────────────────────────────────────────┘
```

### 错误边界（React Error Boundary）

```typescript
interface ErrorBoundaryState {
  hasError: boolean;
  error: Error | null;
}

class ErrorBoundary extends React.Component<
  React.PropsWithChildren<{ fallback?: React.ReactNode }>,
  ErrorBoundaryState
> {
  state: ErrorBoundaryState = { hasError: false, error: null };

  static getDerivedStateFromError(error: Error): ErrorBoundaryState {
    return { hasError: true, error };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 上报到监控系统
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      url: window.location.href,
    });
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? <ErrorFallback error={this.state.error!} />;
    }
    return this.props.children;
  }
}
```

### Core Web Vitals 上报

```typescript
import { onLCP, onCLS, onINP, type Metric } from 'web-vitals';

function reportWebVitals(metric: Metric) {
  // 上报到分析平台
  fetch('/api/vitals', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      name: metric.name,
      value: metric.value,
      rating: metric.rating, // 'good' | 'needs-improvement' | 'poor'
      url: window.location.pathname,
      timestamp: Date.now(),
    }),
    // 使用 keepalive 确保页面卸载时也能发送
    keepalive: true,
  });
}

onLCP(reportWebVitals);
onCLS(reportWebVitals);
onINP(reportWebVitals);
```

## 6. 实战案例：高吞吐量分析仪表盘设计

> 参考 Azure Data Copy 的数据监控场景

### 需求
- 展示 10 万+ 数据点的时序图表
- 实时 WebSocket 更新
- 过滤、下钻、导出功能

### 架构图

```
┌─────────────┐
│   Browser   │
│  ┌───────┐  │     WebSocket      ┌──────────────┐
│  │ React │◄─┼────────────────────┤  Backend WS  │
│  └───┬───┘  │                    └──────────────┘
│      │      │                    ┌──────────────┐
│  ┌───▼───┐  │     REST API       │  REST API    │
│  │React  │◄─┼────────────────────┤  (历史数据)  │
│  │Query  │  │                    └──────────────┘
│  └───┬───┘  │
│      │      │
│  ┌───▼───┐  │
│  │ Web   │  │ (数据聚合、统计计算)
│  │Worker │  │
│  └───────┘  │
└─────────────┘
```

### 关键技术决策

```typescript
// Canvas vs SVG 选择
// > 10k 数据点 → Canvas（DOM 开销低）
// < 10k 数据点 → SVG（可交互、可访问）

// 状态管理
// Server State: React Query（API 数据 + 缓存）
// 实时数据: useReducer + WebSocket（不走 React Query）
// UI 状态: useState（过滤器、选中状态）

// WebSocket 管理
const useWebSocket = (url: string) => {
  const wsRef = useRef<WebSocket>();
  const [status, setStatus] = useState<'connecting' | 'open' | 'closed'>('connecting');

  useEffect(() => {
    const connect = () => {
      wsRef.current = new WebSocket(url);
      wsRef.current.onopen = () => setStatus('open');
      wsRef.current.onclose = () => {
        setStatus('closed');
        // 指数退避重连
        setTimeout(connect, Math.min(1000 * 2 ** reconnectCount++, 30000));
      };
    };
    let reconnectCount = 0;
    connect();
    return () => wsRef.current?.close();
  }, [url]);

  return { ws: wsRef.current, status };
};
```

## 7. 面试深度问答（资深候选人视角）

**Q: 如何设计一个支持 10 个团队、50 个子应用的大型前端平台？**

> "我会分三层来考虑：
> 1. **基础设施层**：设计系统（统一 UI 组件库）、认证（单点登录 SSO）、监控（统一错误上报、性能追踪）。
> 2. **架构层**：用 Module Federation 微前端，每个团队独立仓库、独立部署，通过 Shell 应用集成。共享 React、设计系统包，避免重复加载。
> 3. **治理层**：制定 ADR（架构决策记录）追踪重大决策，统一 CI/CD 流水线模板，强制性能预算（Lighthouse 分数 > 85，bundle > 500kb CI 失败）。
> 在 Azure Data Copy 项目里，我们就是类似的思路：Angular 主应用 + 多个 feature module，每个模块懒加载，ChangeDetectionStrategy.OnPush 保证性能。"

**Q: Redux vs Zustand vs React Query，怎么选？**

> "这不是互斥的选择。我的原则：Server State 用 React Query（数据同步、缓存、loading 状态全包了）；Global UI State 用 Zustand（轻量，无 boilerplate，TypeScript 友好）；只有需要时间旅行调试或团队已在用的情况下才选 Redux Toolkit。过度使用全局状态是常见反模式——大多数状态应该是组件本地的。"

**Q: 遇到过最难的前端性能问题是什么，怎么解决的？**

> "在 Azure Data Copy 的数据网格中，过滤 100 万条记录时 UI 卡死。Chrome DevTools 显示主线程单次任务 3 秒。解决：1) 把过滤计算移到 Web Worker；2) 用虚拟滚动只渲染可见行（react-window）；3) 对过滤输入加 300ms 防抖。最终从 3000ms 降到 60ms 以内，INP 从超标变成 good。"
